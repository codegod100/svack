# Repository Guidelines

## Project Structure & Module Organization
- Svelte 5 UI lives in `src/`; `App.svelte` is the root component, with `index.ts` mounting it and `index.css` supplying global styles. Create new feature modules as additional Svelte components under `src/` or a dedicated subdirectory (e.g., `src/lib/`) to keep concerns scoped.
- `env.d.ts` centralizes ambient TypeScript types, so extend it when introducing new globals.
- `rsbuild.config.ts` enables the Svelte plugin for Rsbuild; adjust this when adding aliases, environment transforms, or additional plugins.
- `backend/` is reserved for API or integration shims; keep browser-only logic out of this folder to avoid bundling server code.
- `dist/` is generated by `pnpm build` and should remain untracked in commits.

## Build, Test, and Development Commands
- `pnpm install` installs dependencies defined in `package.json`.
- `pnpm dev` launches the Rsbuild dev server at `http://localhost:3000`; use for iterative UI work.
- `pnpm build` produces an optimized bundle in `dist/`.
- `pnpm preview` serves the production bundle locally for smoke testing.
- `pnpm svelte-check` runs type and template diagnostics; execute before opening a pull request.

## Coding Style & Naming Conventions
- TypeScript is compiled with strict flags (`tsconfig.json`), so resolve type errors immediately.
- Use two-space indentation across `.svelte`, `.ts`, and `.css` files; prefer single quotes in TypeScript imports and PascalCase for Svelte component filenames.
- Keep CSS class names kebab-case and co-locate component-specific styles within the relevant `.svelte` file.
- Run `pnpm svelte-check` after large refactors to confirm template bindings stay sound.

## Testing Guidelines
- No automated tests ship yet; start with component-level checks using `@testing-library/svelte` or Vitest when adding test coverage.
- Mirror component filenames when creating tests (e.g., `App.test.ts`) under a `src/__tests__/` directory.
- For every new feature, demonstrate expected behavior with `pnpm preview` and attach screenshots or recordings when UI changes are involved.

## Commit & Pull Request Guidelines
- The repository has no existing Git history, so adopt concise, imperative commit subjects (e.g., `Add hero layout`); Conventional Commits (`feat:`, `fix:`) are encouraged for clarity.
- Scope pull requests to a single feature or fix, include a short summary, list validation steps (commands run), and link any tracking issues.
- Capture visual diffs for UI changes and note any configuration updates that require environment action.
